# Как устроен EKS Boundary Matrix CI

В одном репозитории находятся исходный код демонстрации, каталог матриц, исполняемые проверки и GitHub Actions. Матрица описывает правило безопасности. Оракул проверяет это правило по собранным данным. CI связывает изменение кода с нужными матрицами и сохраняет результат.

Связка проекта: **Terraform → AWS VPC и EKS → Kubernetes**, а облачная доставка приложения описана через **GitHub Actions → Docker → Amazon ECR → EKS**. В каталоге сейчас **13 матриц и 42 сценария**. Рабочий локальный путь доставки описан в [Local CD](LOCAL-CD.md).

## 2. Из чего состоит матрица

**Одна матрица — одно связное обязательство на границе системы.** Например, Kubernetes API должен быть доступен через приватный endpoint, а публичный доступ должен быть выключен. Одно обязательство может затрагивать несколько файлов и слоёв.

В `catalog.json` хранится массив `matrices`. Это общий каталог: каждая запись описывает свою границу. JSON задаёт условия проверки; исполняют их отдельные модули JavaScript.

| Поле записи | Смысл |
| --- | --- |
| `id` | Уникальный ID матрицы, например `CLUSTER-ACCESS-01` |
| `boundary` | Между какими участниками или компонентами проходит граница |
| `basis` | `SOURCE_CONTRACT` — правило из изученного исходного кода или зависимости; `PROPOSED_POLICY` — принятое правило демонстрации |
| `source_refs` | ID записей из `source_inventory` в том же каталоге |
| `documentation` | Ключи ссылок из раздела `sources` каталога |
| `obligation` | Что именно должно оставаться истинным |
| `evidence.ci` | Какие наблюдения собирает CI для проверки |
| `evidence.runtime` | Какие наблюдения нужны в развёрнутой среде; само наличие поля не означает, что они уже получены |
| `variants` | Сценарии с ID, типом `positive`/`negative`, условием и ожидаемым результатом |
| `binding` | ID оракула, исполнитель и вид проверяемых данных |
| `implementation_sources` | Пути и символы исходного кода, связанные с реализацией |

Пример существующей матрицы. Для чтения `implementation_sources` сокращён до одного из её реальных участков; остальные поля сохранены:

```json
{
  "id": "CLUSTER-ACCESS-01",
  "boundary": "Deployment network and EKS nodes to the Kubernetes API",
  "basis": "SOURCE_CONTRACT",
  "source_refs": ["SRC-EKS-API"],
  "documentation": ["blueprint_doc", "eks_module_endpoint_defaults", "aws_eks_endpoint"],
  "obligation": "The Kubernetes API has private endpoint access enabled and public endpoint access disabled.",
  "evidence": {
    "ci": "Compare the resolved aws_eks_cluster VPC settings with the expected private and public flags.",
    "runtime": "Compare the deployed EKS endpoint settings with the plan and observe a successful authenticated read from the approved private network."
  },
  "variants": [
    {
      "id": "CLUSTER-ACCESS-01-PRIVATE-P",
      "kind": "positive",
      "case": "Both resolved endpoint flags match the intended private configuration.",
      "expected": "PASS"
    },
    {
      "id": "CLUSTER-ACCESS-01-PUBLIC-N",
      "kind": "negative",
      "case": "An offline plan fixture declares a public endpoint.",
      "expected": "REJECT"
    },
    {
      "id": "CLUSTER-ACCESS-01-NO-PRIVATE-N",
      "kind": "negative",
      "case": "An offline plan fixture has no private endpoint.",
      "expected": "REJECT"
    }
  ],
  "binding": {
    "oracle": "CLUSTER-ACCESS-01",
    "runner": "security/matrix_runtime.mjs",
    "execution": "configuration and controlled fixtures",
    "evidence_domains": ["TERRAFORM_MOCK_STATE"]
  },
  "implementation_sources": [
    {
      "path": "patterns/fully-private-cluster/main.tf",
      "symbols": ["module.eks.0.cluster_endpoint_public_access"]
    }
  ]
}
```

**Матрица и сценарий имеют разные ID.** `CLUSTER-ACCESS-01` — матрица; `CLUSTER-ACCESS-01-PUBLIC-N` — один её сценарий.

## 3. Как связываются исходники и проверки

```text
Файл + символ внутри файла
  → bindings.json: матрицы-кандидаты
  → code_decisions.json: решение для текущего fingerprint
  → catalog.json: обязательство и сценарии
  → matrix_oracles.mjs: проверка по наблюдаемым данным
  → отчёт со статусом и причиной
```

Например, запись в `bindings.json` связывает конкретное поле Terraform с матрицей:

```json
{
  "path": "patterns/fully-private-cluster/main.tf",
  "symbol_prefixes": ["module.eks.0.cluster_endpoint_public_access"],
  "matrix_ids": ["CLUSTER-ACCESS-01"]
}
```

Решение о покрытии хранит `path`, `symbol`, `fingerprint`, `decision`, `matrix_ids`, `variant_ids` и `reason`. Fingerprint — SHA-256 представления участка кода. Новое значение поля меняет fingerprint: прежнее решение больше не считается решением для текущего кода. При удалении участка требуется решение с `change: "deleted"`.

**Привязка показывает, что запускать. Решение фиксирует разбор покрытия. Оракул проверяет соблюдение правила.** Одобрение привязки не превращает нарушенное правило в успешный результат.

## 4. Workflow разработки матриц

```text
Выбираем область проекта и закрепляем версии
  → читаем исходники и поведение используемых зависимостей
  → выписываем границы и обязательства
  → определяем наблюдение, по которому отличим норму от нарушения
  → описываем позитивные и отрицательные сценарии в каталоге
  → реализуем оракулы и варианты тестовых данных
  → связываем код, матрицы и сценарии
  → проводим обратный аудит от исходников к покрытию
  → записываем решения для текущих fingerprints
  → проверяем целостность и полный нормальный прогон
  → отдельно вручную проверяем чувствительность к контрольным поломкам
  → отправляем проверенное изменение на review
```

Обратный аудит задаёт вопрос: **какие правила есть в этом участке кода и чем каждое проверяется?** Его результат для текущей области описан в [`REVERSE_COVERAGE_AUDIT.md`](../security/REVERSE_COVERAGE_AUDIT.md).

Автоматическая инвентаризация поддерживает этот аудит: требует актуального решения для каждого распознанного участка. Смысл нового правила и достаточность сценариев разбирает автор изменения и reviewer.

### Когда нужна новая матрица

| Что изменилось | Решение | Что обновляем |
| --- | --- | --- |
| Уже описанное правило и сценарии полностью подходят | `existing_rule` | Актуальный fingerprint и обоснование привязки |
| Правило прежнее, появился новый способ его нарушить | `add_variant` | Сценарий каталога, исполняемый вариант данных, связи и решение |
| Появилась новая граница или самостоятельное обязательство | `new_matrix` | Матрицу, оракул, позитивный и отрицательный сценарии, связи и решение |
| Изменение не влияет на безопасность в выбранной области | `not_security` | Обоснование; списки матриц и сценариев остаются пустыми |

Например, добавленный формат безопасного health-ответа можно обосновать как `not_security`. Новый доступ приложения к другому хранилищу требует разбора прав, сети и данных: может понадобиться расширение `WORKLOAD-IAM-01` или новая матрица.

При сравнении с базовым коммитом CI проверяет, что решение `new_matrix` действительно добавляет матрицу, а `add_variant` — сценарий. Простая смена названия решения этого не заменяет.

## 5. Что замечает проверка покрытия

Проверяются и **новые файлы**, и **изменения внутри существующих**. Разбор находится в [`change_impact.mjs`](../security/change_impact.mjs), проверка решений и выбор матриц — в [`boundary_review.mjs`](../security/boundary_review.mjs).

| Формат | Единица разбора |
| --- | --- |
| Terraform `.tf`/`.tfvars` | Поле именованного блока: например `module.eks.0.cluster_endpoint_public_access` |
| Kubernetes YAML | Объект и его поля верхнего уровня: например `Deployment.matrix-demo.spec`; вложенная структура `spec` входит в fingerprint целиком |
| Workflow YAML | Поля workflow и отдельные jobs |
| Dockerfile | Инструкции и полный текст файла, включая directives |
| Остальные распознаваемые исходники | Целый файл |

`.git`, `.terraform`, `node_modules` и `artifacts` исключены из обхода. Файлы движка в `security/` и зависимости Node обрабатываются как изменения системы проверок и запускают полный набор. Обычные Markdown-документы в `docs/` не являются исходными единицами.

Перед выбором матриц валидатор проверяет **весь текущий инвентарь**, включая неизменённые файлы. Поэтому старый забытый участок тоже приводит к ошибке покрытия. После добавления локального CD записаны решения для 141 распознанной единицы; это число описывает структуру разбора, а не количество доказанных правил.

## 6. Обычный Boundary Matrix Gate

Workflow: [`.github/workflows/ci.yml`](../.github/workflows/ci.yml). События: Pull Request, push в `main`, ручной запуск и вызов из release workflow.

```text
PR / push main / ручной запуск
  → получение исходников и установка закреплённых инструментов
  → проверка каталога, оракулов, сценариев и привязок
  → проверка решений для всего текущего инвентаря кода
  → тесты целостности самого gate
  → сравнение с базовым коммитом и разбор изменённых/удалённых единиц
  → проверка решений о покрытии изменений
  → выбор затронутых матриц
  → сбор данных из Terraform, Docker, Kubernetes YAML и workflows
  → проверка соответствия данных текущим fingerprints исходников
  → позитивные контроли и отрицательные сценарии выбранных матриц
  → проверка полноты результатов
  → отчёт PASS / FAIL и загрузка артефактов
```

Ошибка инвентаря, каталога или покрытия останавливает выполнение **до запуска оракулов**. Такой результат означает ошибку предварительной проверки; в отчёте может ещё не быть результатов конкретных матриц.

### Как выбираются матрицы

| Ситуация | Что запускается |
| --- | --- |
| Ручной запуск обычного CI или `run --full` | Все 13 матриц |
| Нет базового коммита при первом запуске | Полный набор |
| Есть база для PR/push и актуальные решения | Объединение матриц из подходящих привязок и решений для изменённых единиц |
| Изменено только поле публичности EKS endpoint | `CLUSTER-ACCESS-01`, если остальные исходники и решения не менялись |
| Изменены движок, каталог, политика, зависимости, `ci.yml` или `matrix-sensitivity.yml` | Полный набор |
| Изменена только документация README/`docs/*.md` | Ноль матриц; проверка каталога и тесты целостности продолжают работать |
| Изменён только файл решений | Сам по себе не расширяет выбор; решения всё равно валидируются |
| Участок не классифицирован или нет нужной привязки | Требуется разбор; предусмотренный полный выбор не отменяет ошибку покрытия |

Выбор идёт по участкам кода и связям, поэтому фиксированного правила «любое изменение этой папки запускает N матриц» нет. При нуле выбранных матриц сборка образа и вычисление Terraform в gate пропускаются.

### Что именно проверяется

Terraform проходит `fmt`, инициализацию с lock-файлом, `validate` и `terraform test` с подменёнными AWS, TLS, time, null и cloud-init провайдерами. Из вычисленных ресурсов берутся настройки сети, кластера и IAM. Поддерживаемый набор деклараций IAM проверяется локальными оракулами; неподдерживаемое условие требует `REVIEW`.

Docker собирает **реальный одноплатформенный OCI-образ `linux/amd64`**. Проверка сверяет хеши содержимого и ищет синтетическую секретную метку в конфигурации, истории и слоях. Kubernetes manifests получают repository/digest этого образа и роль из вычисленной конфигурации. Workflow-права читаются из текущих YAML.

Это проверка вычисленной конфигурации и локального артефакта. Создание ресурсов AWS, публикация в ECR и наблюдение работающего кластера относятся к отдельному этапу развёртывания.

### Как читать PASS и FAIL

| Проверка | Наблюдение | Результат сценария |
| --- | --- | --- |
| Позитивный контроль на текущих исходниках | Оракул вернул `PASS` | `PASS` |
| Отрицательный сценарий с подготовленными тестовыми данными | Оракул вернул ожидаемый `FAIL` | `PASS`: нарушение замечено |
| Текущее исходное правило нарушено | Оракул вернул `FAIL` на позитивном контроле | `FAIL` матрицы и CI |
| Нужные данные неизвестны или не поддержаны | Оракул вернул `REVIEW` | Gate не проходит |

Успешный gate требует всех ожидаемых сценариев без пропусков и дублей, успешного нормального контроля и актуальных исходников. Итоговый код выхода обычного gate: `0` при `PASS`, `1` при `FAIL`; ошибка команды или аргументов — `2`.

Падающий workflow создаёт неуспешный GitHub status. Чтобы этот статус обязательно запрещал merge, его нужно включить в required checks правил ветки. Настройка branch protection — отдельный параметр репозитория.

## 8. Ручная проверка чувствительности

Workflow: [`.github/workflows/matrix-sensitivity.yml`](../.github/workflows/matrix-sensitivity.yml), название **Manual Matrix Sensitivity**. Запускается только вручную через `workflow_dispatch`. Автоматического запуска по PR, push или расписанию нет.

```text
Ручной запуск с ID или all
  → валидация каталога и отдельные тесты исполнителя мутаций
  → свежий нормальный контроль: исходное правило должно пройти
  → временная копия исходников
  → одна контрольная поломка исходного файла
  → повторный сбор затронутых данных
  → тот же оракул на новых данных
  → DETECTED / SURVIVED / CONTROL_FAILED / ERROR
  → сверка, что оригинальные файлы не изменились
  → удаление временных копий и сохранение отчёта
```

Для Terraform повторяются вычисление и проверка конфигурации; для YAML повторяются разбор и подстановка значений; для Dockerfile выполняется сборка без кеша с последующим чтением реальных слоёв. Повторно использовать неизменившиеся данные можно только при совпадении происхождения исходников. Кеш бинарников провайдеров общий, исходники и state временных копий раздельные.

| Статус | Значение |
| --- | --- |
| `DETECTED` | Нормальный контроль прошёл, сбор данных успешен, тот же оракул вернул `FAIL` после изменения |
| `SURVIVED` | Изменение дошло до данных, но оракул вернул `PASS` |
| `CONTROL_FAILED` | Исходный нормальный контроль уже не проходит |
| `ERROR` | Не удалось подготовить или проверить данные; сюда относится и `REVIEW` оракула |

Успешный ручной workflow означает, что все выбранные поломки получили **`DETECTED`**. Ошибка сборки сама по себе не считается обнаружением. Изменение оригинального checkout или устаревшие данные также делают прогон неуспешным.

В этой проверке изменённая копия передаётся прямо тому же оракулу через свежие данные. Решения о покрытии намеренно не переоформляются: проверяется именно чувствительность правила, отдельно от остановки обычного gate на неизвестном fingerprint.

**Отрицательные данные в обычных сценариях и изменения исходников — два разных механизма.** Первые входят в обычный CI. Вторые выполняются отдельным ручным workflow. Выбор ID сценария в ручном workflow запускает представительную поломку его родительской матрицы; отдельной исходной мутации для каждого из 42 сценариев нет.

## 9. Как запускать

Среда полного прогона: Linux, Node 22, Terraform 1.13.5, Docker daemon и Buildx. Команды выполняются из корня репозитория.

```sh
npm ci --ignore-scripts
npm run matrix:validate
npm test
```

Полный обычный gate:

```sh
node security/matrix_ci.mjs run --full
```

Выбор по изменению относительно существующего базового коммита:

```sh
node security/matrix_ci.mjs run --base BASE_COMMIT_SHA
```

Отдельные ручные мутационные прогоны:

```sh
node security/matrix_sensitivity.mjs --matrix all
node security/matrix_sensitivity.mjs --matrix CLUSTER-ACCESS-01
node security/matrix_sensitivity.mjs --matrix CLUSTER-ACCESS-01,IMAGE-01
```

В GitHub: **Actions → Boundary Matrix Gate → Run workflow** для полного обычного прогона. Для исходных поломок: **Actions → Manual Matrix Sensitivity → Run workflow → matrix_id**. В поле принимаются ID матрицы, ID сценария, список через запятую или `all`. Неизвестный ID даёт ошибку ввода с кодом `2`.

`npm test` запускает тесты целостности gate. Исходные мутации и их отдельные self-tests в эту команду не входят.

## 10. Где смотреть результат

| Файл в `artifacts/` | Что показывает |
| --- | --- |
| `catalog-validation.json` | Полноту каталога, привязок и решений текущего инвентаря |
| `change-impact.json` | Изменённые файлы, символы и fingerprints |
| `boundary-review.json` | Решения о покрытии изменённых единиц |
| `matrix-selection.json` | Выбранные матрицы и причину выбора |

| `evidence.json` | Данные конфигурации, образа и происхождения исходников |
| `matrix-runtime.json` | Контроль и наблюдение для каждого выполненного сценария |
| `matrix-status.json` и `matrix-status.md` | Итог gate и причины отказа |
| `source-sensitivity/run-*/` | Контроль, изменения файлов, хеши и результаты ручных мутаций |

Если процесс остановился раньше, следующие файлы ещё не создаются. Локальные старые артефакты не являются результатом нового запуска. В GitHub берём артефакт **конкретного run**: `boundary-matrix-evidence` или `manual-matrix-sensitivity`.

Проверенные прогоны исходной базы `39ef230`:

- [Полный обычный CI](https://github.com/Sera5imSec/eks-boundary-matrix-ci/actions/runs/44363323014): 13 матриц, все 41 сценарий прошли.
- [Ручные исходные мутации](https://github.com/Sera5imSec/eks-boundary-matrix-ci/actions/runs/44363397825): каждая из 13 поломок обнаружена, оригинальные исходники сохранились.

В дополнительной проверке 20 ноября 2026 года публичный EKS endpoint, новый неучтённый S3-ресурс и образ `:latest` сначала были остановлены проверкой покрытия. После временного оформления решений для двух изменений соответствующие оракулы также дали `FAIL`: `CLUSTER-ACCESS-01-PRIVATE-P` и `IMAGE-01-DIGEST-P`. Изменения отменены; итоговый полный прогон исходной базы снова дал 41 успешный сценарий.

Поле `verification_status` в каталоге — записанный ранее снимок, а не запрос к GitHub Actions; его строка про hosted CI ещё содержит `PENDING`. Текущий результат конкретного запуска определяется отчётом и статусом этого run.

## 11. Ручной CD и граница текущей проверки

Workflow: [`.github/workflows/release.yml`](../.github/workflows/release.yml), название **Manual EKS Release**.

```text
Ручной запуск на main
  → успешный Boundary Matrix Gate
  → OIDC и выделенная роль публикации
  → сборка и публикация образа в ECR
  → передача repository@sha256:digest
  → OIDC и отдельная роль развёртывания
  → runner внутри приватной сети
  → обновление образа Deployment в namespace matrix-demo
  → ожидание rollout
```

Для реального релиза нужны созданная инфраструктура, bootstrap Kubernetes-объектов, доверие OIDC к точному репозиторию и `main`, переменные GitHub `AWS_PUBLISH_ROLE`, `AWS_DEPLOY_ROLE`, `EKS_CLUSTER_NAME` и Linux runner с меткой `matrix-private-deploy`, AWS CLI и kubectl. Регион workflow — `us-west-2`.

Workflow подготовлен, но успешного развёртывания в AWS у этой исходной базы ещё нет. Обычный CI и ручная чувствительность обходятся без `terraform apply` в облако. Приложение возвращает health-ответ и не вызывает S3: реальный доступ приложения к объекту потребует отдельного наблюдения в развёрнутой среде.
